\section{Test Plan Overview and Objectives}

\subsection{Purpose and scope}
This document defines the verification strategy and reported results for CodeTrail, a
full-stack collaborative coding platform. It covers unit and integration testing,
REST API and Socket.IO testing, meaningful database population, UI and other
non-functional testing, regression verification, and defect tracking.

The scope includes:
\begin{enumerate}
    \item authentication, authorization, profiles and password recovery;
    \item workspace creation, discovery, invitations and role-based access control;
    \item the Monaco multi-file collaborative editor and peer presence;
    \item multi-language Piston code execution, standard input and diagnostics;
    \item SHA-256 activity chaining and forensic tamper auditing;
    \item telemetry, contribution analytics, reports and session validation; and
    \item the interactive terminal and landing-page visual engine.
\end{enumerate}

\subsection{System under test}
The client uses React 19 and Vite. Express 5 controllers expose REST endpoints,
Socket.IO provides real-time collaboration, MongoDB/Mongoose provides persistence,
and Piston v2 provides sandboxed execution. The principal data domains are users,
workspaces, files, sessions, executions and cryptographic activity logs.

\subsection{Test strategy}
\begin{itemize}
    \item \textbf{Unit tests} isolate cryptographic hashing, canonical serialization,
    mathematical aggregation, validation and diagnostic parsing.
    \item \textbf{Integration tests} exercise multi-user sessions, activity chains,
    execution flows and persistence boundaries.
    \item \textbf{API tests} verify request validation, authentication, authorization,
    response bodies and HTTP status codes.
    \item \textbf{Real-time tests} verify rooms, event delivery, cursor throttling,
    deduplication, presence and monotonic versions.
    \item \textbf{Non-functional tests} cover usability, performance, security,
    reliability, offline behavior and browser compatibility.
    \item \textbf{Regression tests} verify previously fixed runtime and workflow bugs.
\end{itemize}

\section{Functional Testing}

\subsection{Cryptographic proof-of-work ledger}
The ledger uses a fixed 64-zero genesis anchor and a canonical payload containing
\code{action}, \code{details}, \code{fileId}, line metrics, sequence, timestamp,
\code{userId} and \code{workspaceId}. Each block is calculated as:
\[
\mathit{currentHash}_n =
\operatorname{SHA256}(\operatorname{CanonicalJSON}(\mathit{payload}_n)
    \mathbin\Vert \mathit{currentHash}_{n-1}).
\]
The reported suite \code{proofOfWork.test.js} verifies deterministic hashing,
avalanche behavior, single-block verification, valid four-block chains, payload
tampering, broken links and sequence gaps. The integrity auditor additionally
detects \code{PAYLOAD\_ALTERED}, \code{CHAIN\_LINK\_BROKEN},
\code{SEQUENCE\_GAP} and \code{TIMESTAMP\_ANOMALY}. All reported checks passed.

\subsection{Telemetry and real-time synchronization}
\code{telemetryStore.js} maintains a 50-event ring buffer, millisecond ISO-8601
timestamps and a monotonic sequence counter initialized at 100. The telemetry
suite reports 7/7 tests passed, including timestamp validity, sequence generation,
hashed envelopes, peer-action recalculation, ring-buffer ordering, active typing
tracking and heartbeat persistence.

\subsection{Analytics, sessions and reports}
The analytics suites verify percentage shares, streak detection, participation
scores and category consistency. The principal score is:
\[
\mathit{score}=(\mathit{linesAdded}\times2)-\mathit{linesDeleted}
                  +(\mathit{executions}\times5).
\]
Session validation covers empty and multi-participant sessions, timestamps,
durations, duplicate sequences, category totals and execution metrics. The
reported boundary test processes 1,500 events from ten participants in under
10\,ms. The contribution-report suite reports 9/9 passed, including ranking,
filters, mathematical validation, SHA-256 certificates and Markdown/HTML export.

\subsection{Seeding objectives}
The seeding harness creates interconnected records so that authentication,
multi-user presence, execution history, contribution analytics and cryptographic
auditing can be demonstrated against meaningful data rather than empty collections.

\subsection{Seeded records}
\begin{itemize}
    \item \textbf{Users:} eight contributor profiles and one academic observer, with
    bcrypt-hashed credentials and role-specific profiles.
    \item \textbf{Workspaces:} JavaScript cloud services, a Python graph engine and
    a C++ memory allocator, each with starter project files.
    \item \textbf{Sessions:} online and offline presence records with active files,
    typing state and accumulated durations.
    \item \textbf{Executions:} successful JavaScript and Python runs, a cryptographic
    test-vector run and a C++ diagnostic record.
    \item \textbf{Activity logs:} a seven-block chain beginning at the 64-zero
    genesis hash and containing file, edit, execution and membership actions.
\end{itemize}

\subsection{Performance and concurrency}
\begin{itemize}
    \item Cursor broadcasts are limited to one packet per 30\,ms window (about 33
    packets per second), reducing continuous-drag traffic by the reported 91\%.
    \item Analytics process 1,500 events across ten participants, aggregating 10,500
    lines with no overflow and a reported duration below 10\,ms.
    \item Local Piston latency is reported at 30--55\,ms; cloud fallback at
    380--720\,ms. Code above 256\,KB and stdin above 128\,KB are rejected early.
    \item Oxlint reports zero errors across 46 frontend files and 92 rules.
\end{itemize}

\subsection{Security and authorization}
Tests cover SHA-256 tamper evidence, role enforcement for owner/admin/editor/viewer,
bcrypt password storage, one-hour reset tokens from secure random bytes, and
sandbox execution limits. Tamper vectors include altered payloads, broken links,
sequence gaps and timestamp regressions.

\subsection{Reliability and compatibility}
Database-dependent routes return HTTP 503 when MongoDB is unavailable. The editor
stores offline changes locally and reconciles them after reconnection. Duplicate
activity sequences are protected by a compound index and retried with bounded
backoff. Chrome, Edge, Firefox and Safari are reported compatible with Monaco,
WebSockets and execution workflows.

\subsection{Detailed example: role normalization}
The ActivityLog schema originally accepted canonical roles only, while new users
could have the display role ``CodeTrail Learner''. The corrective normalization
maps canonical values directly, maps owner/admin/viewer terms explicitly, and
falls back to editor for the learner display role. The runtime regression suite
reports successful preservation of canonical roles and successful normalization.
